## 1. What was decided

[CUSTOM: Rust port execution model] The Rust port is organized as **suite tickets**
and gated by **assertion-ID parity**, not by rough grep counts.

A suite ticket is:

```text
one legacy entry suite
+ imported *-suite step modules
+ all legacy assertion IDs
+ dependency wave / assertion style
+ Rust port module
+ coverage/security evidence
```

The legacy backend assertion inventory is generated by AST from
`test/backend/deno/**/*.test.ts(x)` and imported `*-suite/*.steps.ts` modules.
Each assertion call site receives a stable ID:

```text
L:<sha1-16>-<occurrence>
```

Rust port assertions must map one-to-one to those IDs using either:

```rust
// parity-assert: L:<id>
assert_eq!(...);
```

or a parity macro:

```rust
parity_assert_eq!("L:<id>", ...);
```

## 2. Commands

```bash
npm run vendor:repair                  # restore missing vendored files, checksum-verified
npm run test:assert-parity:inventory   # regenerate checked-in legacy inventory
npm run port:workboard                 # regenerate suite queue
npm run test:rust:map                  # validate legacy-suite -> Rust module map
npm run test:assert-parity:report      # drift/invalid-mapping report
npm run test:assert-parity             # final gate: all legacy IDs mapped exactly once
```

## 4. Staging model

The port proceeds in dependency waves:

1. Foundation: health/setup, auth, sessions, 2FA, idempotency.
2. Admin plane: capabilities, orgs, clusters, teams, systems, users, settings.
3. Request lifecycle: state machine, submission/decision/owner flows, concurrency.
4. Credential delivery: direct links, secret material, AWS exchange.
5. Physical custody.
6. Observability, notifications, cron.
7. Integrations/identity: Entra, Slack, invites, identity change.
8. Security/coverage closure: OWASP and cross-cutting matrices.
9. Cargo seam re-ports: clock/logger/query-count/schema seams.

Security negatives travel with their routes; wave 8 is closure, not permission to
defer auth/IDOR/injection assertions. Seam tests are pulled forward when they
unblock later waves.

## 5. Definition of done

A suite ticket is done only when:

- every legacy assertion ID in the ticket is mapped to a Rust assertion;
- the Rust test targets the real Rust binary or a documented Rust-native seam;
- the mapped assertion preserves the original behavior/intent;
- coverage/security evidence is recorded;
- the relevant Rust tests pass.

The whole port is complete only when `npm run test:assert-parity` passes with
4,272 / 4,272 mapped assertion IDs and no unannotated Rust port assertions.

### Per-suite ownership gate (strengthened)

`scripts/check-rust-test-map.mjs` now checks, for every `ported` suite, that its
Rust module contains **exactly** the frozen inventory ID set for that legacy
suite (no missing, foreign, or duplicate IDs) and that `mappedAssertions`
equals the legacy count. Partial suites must report their actual subset size.
This closes the "right total, wrong suite" hole: global count equality alone
cannot prove a one-to-one port. Semantic intent is still reviewed against the
legacy scenario during porting (Stage 2C caught and repaired an
`admin_systems` ID-order drift that count/order checks had missed).

### Stage 4A delivery note (2026-10-30)

Stage 4A maps four direct-delivery suites and 136 literal assertion IDs to Rust; the full Rust workspace regression passed (`ported_suites` 179/179, 1472.21s); cumulative mapped assertions are 2,602 of 4,272 (1,670 pending; no unannotated Rust asserts). The real Rust app now implements recipient-scoped, TTL-limited opaque links, atomic usage tracking, 2FA-gated and live-visibility reauthorization, and rendered Handlebars direct-link anchors in request notifications. The request submission path creates an RSA-2048 keypair and returns an AES-256-GCM-wrapped PKCS#8 download (or accepts a validated client SPKI public key), while `GET /requests/:id/secret-material` yields the KEK only to the submitter, inside the activity window, in an eligible state, **after** delivery lands. Fixture payloads use real RSA-OAEP/AES-GCM encryption and are decrypted end-to-end. Self-service password change and admin 2FA/password resets revoke sessions and record audit events. AWS/LocalStack exchange and transport remain Stage 4B (184 assertions); seeded delivery is explicitly not a fake exchange implementation.

The frozen inventory counts *call sites*, not their runtime iteration count: e.g. one legacy `assertEquals` inside a 200-key loop is one ID, and four assertions inside `assertOutboxHasDirectLink` retain their own helper IDs separate from each call site's assertion. The map gate checks suite-level exact ID sets and counts; test execution ensures the assertions evaluate against real Rust responses/DB rows.

Direct-link notification scope follows the current request writer: a notification with exactly one recipient has an intended-user-bound key; a team notification with multiple recipients has an unscoped locator and is reauthorized by `req_can_view` on resolve. This is **not** a replacement for a per-recipient minting strategy. Email template rendering is linked to seeded global templates; organization overrides and non-request trigger writers remain future integration work.
